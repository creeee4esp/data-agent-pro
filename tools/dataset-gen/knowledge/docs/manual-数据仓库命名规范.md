# 数据仓库命名规范

## 适用范围

命名规范覆盖本公司数据仓库里所有分析用的表、字段、分区和指标，不区分计算引擎。只要一张表最终会被数据分析师、业务同事或自动写 SQL 的数据智能体检索到，它的名字就要符合这里的条款。

把这件事说清楚的原因很简单：现在库里一共有 123 张有效表和 3175 张噪声表，噪声是有效表的二十多倍。新同事如果没有一套可以照着念的命名约定，很容易把一张 `ads_item_review_score_monthly_bak_20250221` 当成正式表去取数，结果拿到的是某一天的临时快照。

规范条款分三类：

1. 强制条款，用"必须""禁止"表述，评审时一票否决。新建的有效表若违反强制条款，不允许上线。
2. 推荐条款，用"应当""建议"表述，允许在有充分理由时偏离，但要在评审记录里写明理由。
3. 例外说明，专门描述历史遗留的噪声表，它们不需要整改命名，但必须被识别、被隔离，不能进入分析口径。

适用对象包括五个分层前缀 `ods_`、`dim_`、`dwd_`、`dws_`、`ads_` 下的所有表，也包括没有前缀的历史分表（例如 `item_review_202301`）。前者是我们要长期维护的资产，后者是要逐步清理的负债，两者都在本规范的管辖之内，只是处理方式不同。

凡是本规范未覆盖的新场景，先按最接近的条款类推，再提交命名评审补充条款，不要私自发明新的前缀或后缀。

## 分层前缀

分层前缀是读名字时第一眼要看的信息，必须是 `ods_`、`dim_`、`dwd_`、`dws_`、`ads_` 五者之一，顺序代表数据从贴源到应用的加工方向。

1. `ods_` 表示贴源层，保存与业务系统结构基本一致的原始数据，禁止在表名里再堆叠加工语义。
2. `dim_` 表示维度层，存放可供多处关联的维度，例如 `dim_user_his` 这种带 `_his` 后缀的就是维度表的历史归档副本，不是当前维表。
3. `dwd_` 表示明细层，保存清洗后的事实明细，例如 `dwd_item_review_di_old`、`dwd_trade_pay_di_old` 都带了 `_old`，说明它们是明细表的旧版本，不能当正表用。
4. `dws_` 表示汇总层，按域、粒度、事件、周期做轻度聚合。
5. `ads_` 表示应用层，直接面向报表和业务口径，例如 `ads_trade_gmv_daily`、`ads_pay_channel_monthly`。

强制要求：

- 有效表必须以上述五个前缀之一开头，前缀一律小写、带下划线。
- 禁止把两个分层前缀拼在同一张有效表上，例如不允许把 `dws` 和 `ads` 两个前缀叠写在同一个名字里。
- 没有前缀的表（如 `log_visit_202301`）一律视为历史遗留，不得新建，也不得在新的加工链路里引用。

读名字判断分层时，只认开头的前缀，不要被中间的词迷惑。像 `test_ads_item_review_score_monthly` 虽然中间有 `ads`，但开头是 `test_`，它是测试表，不是应用层正表。

## 表名结构

表名结构从左到右按"前缀 + 业务域 + 粒度 + 事件 + 周期"的次序排列，层层收窄语义，读者从左往右读一遍就能大致猜出这张表装的是什么。

以 `dws_trade_prov_order_1d` 为例，拆开看就是：`dws_` 是汇总层，`trade` 是交易域，`prov` 是省份粒度，`order` 是下单事件，`1d` 是日周期。这种结构的完整定义是 `dws_<域>_<粒度>_<事件>_<周期>`。

1. 业务域必须用团队公认的缩写，例如交易 `trade`、商品 `item`、物流 `lgs`、优惠券 `coupon`、支付 `pay`。
2. 各段之间只用单个下划线连接，禁止出现双下划线或连字符。
3. 段的顺序不得调换，粒度一定在事件之前，周期一定在最后。
4. 表名整体小写，禁止大写字母和中文。

反例要特别警惕带日期尾巴的名字。`ads_trade_cate1_sales_monthly_bak_20250309` 看起来像在结构末尾加了日期段，其实 `_bak_20250309` 不是合法的周期段，而是"备份 + 备份日期"，这类名字一共 510 张，全部是噪声。合法的周期段只有固定的几种写法，见下一章。

命名时先把业务含义想清楚再拼名字，不要先建表再回头补语义，否则很容易拼出结构不对、后面谁都看不懂的表。

## 统计周期后缀

统计周期后缀写在表名最末尾，`dws_` 层用 `1d`、`1w`、`1m` 表示日、周、月三种粒度，`ads_` 层用 `daily`、`monthly` 这类英文单词表示报告期。

1. `dws_` 汇总表的周期后缀必须是 `1d`、`1w`、`1m` 之一，分别对应一天、一周、一个月的聚合窗口，例如 `dws_trade_prov_order_1d` 是按日聚合。
2. 同一个业务含义的日、周、月表构成一个家族，家族名去掉周期后缀后应当完全一致，例如 `dws_trade_brand_order`、`dws_trade_cate1_order` 就是两个家族各自的前缀。
3. `ads_` 报表表用自然语言周期词，`ads_trade_gmv_daily` 是按天出的 GMV 报表，`ads_coupon_usage_monthly`、`ads_item_review_score_monthly`、`ads_lgs_delivery_monthly`、`ads_pay_channel_monthly`、`ads_trade_cate1_sales_monthly` 都是按月出的报表。
4. 禁止用纯数字年月日充当周期后缀。`item_review_202301` 末尾的 `202301` 是分表月份，不是周期粒度，它表示这张表只装了 2023 年 1 月那一段数据，属于月分表，这类表一共 216 张。`item_review_20250101`、`lgs_shipment_20250101`、`log_visit_20250101` 末尾是具体某一天，属于日分表，这类表一共 1825 张。

判断一张表是不是正式周期表，看后缀是不是固定词；一旦后缀是 `20250101` 这种具体日期，基本就是分表或带日期的备份，不能进分析口径。

## 粒度与事件命名

粒度与事件这两段决定了一行数据代表什么，必须用团队统一的缩写，不能各写各的。

1. 粒度段描述聚合到哪一层，常见取值有品牌 `brand`、一级品类 `cate1`、单品 `sku`、省份 `prov`、承运商 `carrier`、仓库 `warehouse`。例如 `dws_item_brand_review`、`dws_item_cate1_review`、`dws_item_sku_review` 分别是商品评价按品牌、一级品类、单品聚合。
2. 事件段描述这张表记录的业务动作，常见取值有下单 `order`、评价 `review`、发货 `ship`。例如 `dws_lgs_carrier_ship`、`dws_lgs_prov_ship`、`dws_lgs_warehouse_ship` 都是物流发货事件，只是粒度分别是承运商、省份、仓库。
3. 同一事件在不同粒度下要复用同一个事件词，`dws_trade_brand_order` 和 `dws_trade_cate1_order` 都用 `order`，不允许一个写 `order` 一个写 `ord`。
4. 粒度和事件都必须是已登记的缩写，新增缩写要走命名评审，不能临时造词。

容易踩的坑是把粒度和事件写反。规范要求粒度在前、事件在后，读起来是"在某个粒度上统计某个事件"。如果拿不准某个缩写是否已登记，先查家族清单里的现有表，照着现有写法来，比自己发明省事也更不容易出错。

## 字段命名

字段命名统一用小写蛇形，语义优先，让人不看注释也能猜个八九不离十，这一条对自动写 SQL 的数据智能体尤其重要。

1. 字段名必须小写字母加下划线，禁止大写、驼峰和中文。
2. 布尔语义字段用 `is_` 开头，例如 `is_paid`。
3. 金额字段带 `amount` 或 `amt`，数量字段带 `cnt` 或 `qty`，时间字段带 `time` 或 `date`，命名时沿用同类字段已有的词根，不要同义词混用。
4. 禁止用无意义的缩写或拼音首字母当字段名。

要特别提醒一个历史坑：备份表和个人副本里的字段名常常和正表对不上。像 `u_chenqi_channel_monthly_tmp`、`u_chenqi_coupon_di_analysis`、`u_chenqi_coupon_receive_analysis` 这类个人副本一共 345 张，它们的列可能被改过名或删过列，直接拿来和正表关联就会报错或错配。统计口径里只认正表的字段定义，副本字段不作数。

新建字段时，先在同域的有效表里找有没有同义字段，优先复用已有命名，保证同一个业务含义在全仓库只有一种写法。

## 日期与分区字段

日期与分区字段要把"数据按哪天分区"和"业务发生在哪天"分开，这是取数不出错的关键。

1. 分区字段统一叫 `dt`，表示分区日期，用于按天切分物理存储，取数时用来圈定要扫描的分区范围。
2. 业务日期另有专门字段，例如 `order_date`、`pay_date`，表示下单、支付这些业务动作真正发生的日期。
3. 强制区分：`dt` 不等于业务日期。一条支付记录可能在 `pay_date` 当天发生，却因为补数而落在另一个 `dt` 分区里，统计业务口径必须用业务日期字段，过滤分区才用 `dt`。
4. ADS 月报表用自己的统计周期字段，例如 `ads_item_review_score_monthly` 这类月报用 `stat_month` 标识报告月，不要去它上面找 `dt`。

常见错误是图省事，所有过滤都写在 `dt` 上。按 `dt` 统计 GMV，会把补数、回刷造成的分区错位算进来，口径就不准了。正确做法是：圈数据范围用 `dt`，算业务指标按 `order_date` 或 `pay_date` 归属。

写 SQL 之前先确认这张表到底有没有 `dt`、业务日期字段叫什么，ADS 月报是不是 `stat_month`，不要凭印象套字段名。

## 指标字段命名

指标字段命名要让名字自带口径信息，看到字段名就能判断它是计数、金额还是比率，以及能不能跨行相加。

1. 计数指标用 `_cnt` 结尾，例如订单数、评价数。
2. 金额指标用 `_amount` 或 `_amt` 结尾，分别用于明细金额和汇总金额，同一张表里保持一致。
3. 比率指标用 `_rate` 结尾，例如退款率。比率字段一律不可直接跨行相加求总，必须用分子分母重新计算。
4. 平均值指标用 `avg_` 开头，例如平均评分、平均时长，同样不可简单相加。
5. 指标字段名要和它所在表的事件对应，下单事件表里的订单数就叫订单相关的 `_cnt`，不要借用其他事件的词。

命名时顺带表达可加和性：带 `_cnt`、`_amount` 的多数是可加和的度量，带 `_rate`、`avg_` 的是不可加和的派生量。自动写 SQL 的智能体会依赖这条约定决定是 `SUM` 还是重算，所以命名一旦含糊，口径就会错。

反例是把比率字段命名得像计数字段，让人误以为可以 `SUM`。遇到拿不准的指标，宁可名字长一点也要把口径写清楚，不要为了短而牺牲可读性。

## 噪声表命名与识别

噪声表指不该进入分析口径的表，当前库里一共 3175 张，远多于 123 张有效表，识别它们是取数前的第一道关卡。

噪声表按命名特征分成以下几类，每类都有可直接识别的后缀或前缀：

1. 历史归档，以 `_his` 结尾，例如 `ads_coupon_usage_monthly_his`、`ads_trade_gmv_monthly_his`、`dim_user_his`，共 13 张。
2. 备份，以 `_bak` 结尾，例如 `ads_item_review_score_monthly_bak`、`ads_lgs_delivery_monthly_bak`、`ads_pay_channel_monthly_bak`，共 98 张。
3. 带日期备份，以 `_bak_日期` 结尾，例如 `ads_item_review_score_monthly_bak_20250221`、`ads_lgs_delivery_monthly_bak_20250217`、`ads_trade_cate1_sales_monthly_bak_20250309`，共 510 张。
4. 旧版本，以 `_old` 结尾，例如 `ads_trade_refund_rate_monthly_old`、`dwd_item_review_di_old`、`dwd_trade_pay_di_old`，共 44 张。
5. 测试表，以 `test_` 开头，例如 `test_ads_item_review_score_monthly`、`test_ads_pay_channel_monthly`、`test_ads_trade_cate1_sales_monthly`，共 58 张。
6. 月分表，以 `_年月` 结尾且无分层前缀，例如 `item_review_202301`、`lgs_shipment_202301`、`log_visit_202301`，共 216 张。
7. 日分表，以 `_年月日` 结尾且无分层前缀，例如 `item_review_20250101`、`lgs_shipment_20250101`、`log_visit_20250101`，共 1825 张。
8. 临时表，以 `tmp_` 开头，例如 `tmp_aftersale_order_0221`、`tmp_category_di_1226`、`tmp_channel_monthly_0407`，共 66 张。
9. 个人副本，以 `u_<用户>_` 开头，例如 `u_chenqi_channel_monthly_tmp`、`u_chenqi_coupon_di_analysis`、`u_chenqi_coupon_receive_analysis`，共 345 张。

识别规则：凡命中上述任一特征的表，一律不得用于对外口径。即便某张备份表看起来字段更全，也可能缺列或列名被改，统计只认正表。

## 命名评审流程

命名评审流程是新表上线前的必经环节，目的是把不合规的名字挡在上线之前，而不是上线之后再回头改。

1. 提交：建表人填写申请，写明拟用表名、分层前缀、业务域、粒度、事件、周期，以及这张表属于 123 张有效表里的哪一类资产。
2. 自检：建表人先对照本规范逐条核对，确认前缀合法、结构正确、周期后缀是 `1d`/`1w`/`1m` 或 `daily`/`monthly`，且名字不带 `_his`、`_bak`、`_old`、`test_`、`tmp_`、`u_` 等噪声特征。
3. 评审：评审人检查名字是否与现有家族冲突、缩写是否已登记、分区字段是否规划了 `dt`、业务日期字段是否齐备。强制条款不通过的一律打回。
4. 登记：通过后把新表登记进有效表清单，新增的业务域或粒度缩写同步补进缩写表。
5. 噪声隔离：评审时若发现申请的名字其实是某张正表的备份或测试版，要求改为合规正表名或并入已有家族，不允许新增噪声。

评审的底线是：宁可在上线前多花十分钟核名字，也不要让又一张来路不明的表混进那 3175 张噪声里。流程跑顺之后，大家建表会越来越快，因为能照抄的合规样板越来越多。
