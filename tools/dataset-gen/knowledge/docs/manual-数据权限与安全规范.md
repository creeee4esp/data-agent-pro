# 数据权限与安全规范

本规范面向数据仓库全量表资产，约定分层、敏感字段、权限、导出与审计口径。当前仓库共有有效表 123 张，另有噪声表 3175 张（历史归档、备份、带日期备份、测试表、旧版本、月分表、日分表、临时表与个人副本），两类表的权限策略完全不同，读者在申请与取数时必须先判断目标是不是有效表。

## 数据分级

数据分层前缀固定为 `ods_`、`dim_`、`dwd_`、`dws_`、`ads_` 五类，所有有效表必须落在这五个前缀之内，分级与分层一一对应，便于按前缀批量授权。

1. 贴源层 `ods_` 承载原始明细，默认划为受限级，只对数据工程与少数经审批的分析师开放，不直接对业务同事放开。
2. 明细层 `dwd_` 为清洗后的事实明细，按业务域授权；维度层 `dim_` 为公共维度，划为内部通用级，示例如 `dim_user_his` 这类带 `_his` 后缀的历史归档表不属于可对外授权的有效维度表，申请时不要误选。
3. 汇总层 `dws_` 与应用层 `ads_` 风险相对低，是业务同事和数据智能体取数的主入口。`dws_` 命名遵循 `dws_<域>_<粒度>_<事件>_<周期>`，周期取 `1d` / `1w` / `1m`，例如 `dws_trade_prov_order_1d`；应用层如 `ads_trade_gmv_daily`、`ads_pay_channel_monthly` 为面向报表的成品。
4. 分级一经确定随表生命周期固定，字段新增导致敏感度上升时必须重新评级，不得沿用旧级别。

容易误用的一点：以 `ads_` 开头不等于一定是有效表。`ads_trade_gmv_monthly_his`、`ads_item_review_score_monthly_bak`、`test_ads_pay_channel_monthly`、`ads_trade_refund_rate_monthly_old` 虽然前缀合规，但分别属于历史归档、备份、测试表、旧版本，应按噪声表最低权限处理，不授予常规读取权限。

## 敏感字段

敏感字段指可直接或间接定位到自然人、交易与金额的列，需在表级分级之上再做列级标记。无论表处在哪一层，只要含敏感字段，都要在权限与导出环节单独处理。

1. 个人身份类字段（如用户标识、手机号、收货地址等）标记为高敏感，默认在授权视图中脱敏，不随普通读权限下放原文。
2. 交易与金额类字段标记为中敏感，`ads_trade_gmv_daily`、`ads_trade_cate1_sales_monthly` 这类成品表中的金额指标可按汇总粒度开放，但明细层 `dwd_trade_pay_di_old` 一类旧版本明细不得作为敏感字段的授权来源。
3. 物流与渠道类字段（如承运商、仓库、支付渠道）标记为低敏感，`dws_lgs_carrier_ship`、`dws_lgs_warehouse_ship`、`ads_pay_channel_monthly` 可按业务需要正常授权。
4. 敏感字段标记随表进入血缘下游，由 `dwd_` 加工进 `dws_`、`ads_` 的过程中不得降级，除非在加工中已做聚合或脱敏并通过评审。

容易误用的一点：聚合不等于脱敏。即便在 `dws_trade_cate1_order` 做了类目汇总，只要结果仍能反查到少量用户，金额与身份字段仍按原敏感级管控。

## 权限申请

权限申请的对象只能是有效表，申请单须写明目标表名、字段范围、用途与有效期，按表所在分层走对应审批链。有效表共 123 张，其余 3175 张噪声表不受理常规授权。

1. 申请 `ods_`、`dwd_` 明细权限的，需业务负责人与数据负责人双签；申请 `dws_`、`ads_` 读权限的，由数据负责人单签即可，例如申请 `dws_trade_brand_order` 或 `ads_coupon_usage_monthly` 的只读权限走单签流程。
2. 申请单必须精确到表名，不接受前缀通配。写 `ads_*` 或 `dws_lgs_*` 批量申请的一律退回，须逐表列明，如 `dws_lgs_prov_ship`、`dws_lgs_warehouse_ship` 分别列出。
3. 含高敏感字段的授权默认签发脱敏视图权限，原文权限需额外说明理由并加签。
4. 权限默认有限期，到期自动回收；长期取数岗位可申请续期，但每次续期都要复核用途是否仍成立。

容易误用的一点：不要把带日期备份表当成当期表申请。看到 `ads_lgs_delivery_monthly_bak_20250217` 时，正确做法是申请对应有效表 `ads_lgs_delivery_monthly`，备份表不授予读权限。

## 个人副本表

个人副本表指以 `u_<用户>_` 开头的用户私有表，当前共 345 张，如 `u_chenqi_channel_monthly_tmp`、`u_chenqi_coupon_di_analysis`、`u_chenqi_coupon_receive_analysis`，默认只有创建者本人可见。

1. 个人副本只用于本人临时分析，权限不对外开放，不得作为报表、看板或下游任务的数据来源。
2. 严禁把生产取数指向个人副本。如果看到任务读取 `u_chenqi_coupon_di_analysis`，应改读对应有效表（如 `ads_coupon_usage_monthly`），个人副本随时可能被创建者删除或改写。
3. 个人副本内若落入了敏感字段，责任由创建者承担，须比照源表敏感级自行管控，不得转发给他人。
4. 离职或转岗时，本人名下的 `u_<用户>_*` 表一并随账号处理，不做移交，需要留存的内容应先沉淀为正式有效表。

容易误用的一点：数据智能体写 SQL 时如命中 `u_chenqi_*` 之类表名应直接排除，这类表不在对外可查范围内。

## 导出管理

导出管理约束把仓库数据落到本地文件、邮件或外部系统的行为，导出对象必须是已授权的有效表，导出动作全程留痕。

1. 导出前须确认目标表为有效表且本人持有有效权限，禁止导出噪声表；从 `test_ads_trade_cate1_sales_monthly`、`ads_coupon_usage_monthly_his` 导出数据属于违规。
2. 含高敏感字段的结果默认不允许导出原文，只能导出脱敏或聚合后的结果，如需导出 `ads_pay_channel_monthly` 的渠道汇总可放行，但不得附带可反查用户的明细。
3. 单次导出设行数上限，超限须走额外审批；批量、定时导出视同数据外发，按最严口径加签。
4. 导出文件须标注来源表名、`dt` 分区与导出时间，便于后续追溯。

容易误用的一点：把备份表当成"稳定快照"导出是常见错误。`ads_item_review_score_monthly_bak` 并非官方发布口径，导出它会把一份来历不明的数据扩散出去。

## 脱敏规则

脱敏规则规定高敏感与中敏感字段对外呈现时的变形方式，脱敏在授权视图层统一实施，取数方看到的即脱敏后结果。

1. 身份类字段采用掩码或哈希，不保留可逆原文；除非持原文权限，任何从 `dwd_`、`ods_` 向下游如 `dws_item_sku_review` 的加工都应基于脱敏后的键。
2. 金额与交易字段在汇总表中按粒度呈现，`dws_trade_cate1_order`、`ads_trade_cate1_sales_monthly` 对外只给类目级汇总，不下放到可识别单笔交易的粒度。
3. 脱敏策略随字段敏感级确定，不得由取数方在查询中自行"还原"；发现绕过脱敏的查询按违规处理。
4. 脱敏与分区解耦：无论查询哪个 `dt`，脱敏规则一致，不因历史分区而放松。

容易误用的一点：别用旧版本表绕过脱敏。`dwd_item_review_di_old`、`dwd_trade_pay_di_old` 可能保留了未脱敏的历史列，这类旧版本表已不维护，严禁作为取数来源。

## 审计

审计覆盖建表、授权、查询、导出与删除全过程，所有动作按表名与账号留痕，审计日志按 `dt` 分区留存以便回溯。

1. 对有效表的每次读取、导出都记录账号、表名、字段范围与时间；对 `ads_trade_gmv_daily`、`dws_trade_prov_order_1d` 等核心表重点监控异常访问。
2. 对噪声表的访问同样留痕：频繁访问 `*_bak`、`*_his`、`test_*`、`*_old` 的账号会被重点排查，因为正常业务不应依赖这些表。
3. 个人副本 `u_<用户>_*` 的创建与增长纳入审计，345 张的规模若持续上升需要专项治理。
4. 审计发现越权、绕脱敏、超量导出的，先冻结相关权限再核实。

容易误用的一点：审计不只看有效表。大量命中带日期备份（如 `ads_trade_cate1_sales_monthly_bak_20250309`）往往说明取数口径选错，需要在审计中主动纠偏。

## 账号管理

账号管理约定数据平台账号的开通、权限绑定与回收，账号与自然人一一对应，权限随账号而非随个人副本表流转。

1. 账号开通时默认不含任何表权限，所有读写都通过权限申请单逐表授予。
2. 服务账号（调度、智能体）与个人账号分离：数据智能体使用的账号只授予有效表只读权限，禁止其访问 `tmp_*`、`u_<用户>_*` 等非正式表。
3. 账号权限定期复核，长期未使用的授权回收；一个账号名下积累的个人副本如 `u_chenqi_*` 须随复核一并清点。
4. 转岗按新岗位重授权，不沿用旧权限；离职当日回收全部权限并冻结账号。

容易误用的一点：共享账号会让审计失效。严禁多人共用一个账号取数，否则 `u_chenqi_channel_monthly_tmp` 这类以某人命名的表将无法对应到真实责任人。

## 违规处理

违规处理针对越权访问、绕过脱敏、超量导出、滥用噪声表等行为，依据审计证据分级处置，处置记录随账号留存。

1. 一般违规（如误从 `ads_coupon_usage_monthly_his` 取数、未按脱敏口径查询）先通报并要求整改，限期改回有效表口径。
2. 严重违规（导出高敏感原文、绕过脱敏、将个人副本 `u_chenqi_coupon_di_analysis` 作为生产来源）立即冻结相关权限并上报。
3. 把测试表、旧版本表用于对外报表（如用 `test_ads_item_review_score_monthly` 出结论）视为数据事故，按事故流程复盘。
4. 屡次违规或造成数据外泄的，收回数据平台账号并追责。

容易误用的一点：不要以"只是看看"为由访问噪声表。审计不区分意图，访问 `*_old`、`*_his`、`*_bak` 本身就会计入排查范围。

## 常见问题

常见问题汇总取数方最容易踩的坑，按"看到什么表、应该怎么办"的方式给出答案，便于单独检索。

1. 看到前缀合规但结果异常的表怎么办：先确认是不是噪声表。仓库里有效表仅 123 张，噪声表多达 3175 张，`ads_...._bak`、`...._his`、`test_...`、`...._old` 都不是当期口径。
2. 想要某月数据却找到一堆带日期的表怎么办：带日期备份（510 张）和日分表（1825 张，如 `log_visit_20250101`）、月分表（216 张，如 `item_review_202301`）都不是正式表，应回到对应有效表并用 `dt` 分区筛选。
3. 需要长期复用自己的中间结果怎么办：不要停留在 `u_<用户>_*` 个人副本或 `tmp_*` 临时表（66 张，如 `tmp_channel_monthly_0407`），应申请沉淀为正式有效表。
4. 数据智能体选表时怎么避坑：只在 123 张有效表范围内选，命中 `_bak` / `_his` / `_old` / `test_` / `tmp_` / `u_` / 纯日期后缀的表名一律排除。

容易误用的一点：`dt` 是分区日期，不等于业务日期。筛选成交或支付时间要用业务日期字段如 `order_date`、`pay_date`，不要误把 `dt` 当作下单或支付当天。
