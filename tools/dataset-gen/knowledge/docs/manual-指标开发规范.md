# 指标开发规范

## 指标分类

指标分为原子指标、派生指标两大类，所有新指标开发前必须先归类，再决定落在哪一层、怎么算。

1. 原子指标：不可再拆的基础度量，直接从明细聚合得到，例如下单数、支付金额。
2. 派生指标：由原子指标经四则运算或加筛选条件得到，例如退款率、客单价。
3. 归类先行：先确定一个指标是原子还是派生，再写计算规则，顺序不能反。
4. 分层对应：原子指标在 `dwd_`、`dws_` 层沉淀，派生指标多在 `dws_`、`ads_` 层或查询时计算。
5. 口径唯一：同一业务含义的指标全库只允许一个定义，禁止多处各算各的。

归类的意义是统一口径的起点。原子指标定准了，派生指标才有可靠的分子分母。例如 `ads_trade_gmv_daily` 里的 GMV 是原子度量，客单价是在它基础上派生，两者不能混为一谈。全库 123 张有效表都要按这套分类登记指标，不允许同一业务含义在多张表里出现互相打架的两套算法。分类还决定了取数路径：原子指标直接聚合即可，派生指标必须回到原子层重算，不能在派生结果上再做派生，否则误差会逐级累积，最后谁也说不清这个数到底是怎么来的。

## 原子指标

原子指标是直接从明细或轻度汇总聚合出的基础度量，是全仓库口径的地基。

1. 来源单一：每个原子指标只认一张定稿来源表，优先取 `dwd_` 明细或对应的 `dws_` 汇总。
2. 可加和优先：计数、金额类原子指标应设计为可加和，便于跨维度 `SUM`。
3. 标注口径：原子指标须写明统计事件、日期归属字段、过滤条件。
4. 正表取数：聚合原子指标只能用有效表，禁止用 `_bak`、`_old`、`test_`、`tmp_` 等噪声表。
5. 示例：GMV、支付订单数属原子指标，可从 `dws_trade_prov_order_1d` 这类汇总表聚合。

原子指标一旦定义，向上会被大量派生指标复用。例如 `dws_trade_brand_order` 家族里的订单数、支付金额，是品牌维度一切派生分析的基础。地基错一行，上层全错。选来源表时要特别警惕噪声：库里有 3175 张噪声表，像 `dwd_trade_pay_di_old` 这种 `_old` 旧版本、`ads_pay_channel_monthly_bak` 这种 `_bak` 备份，字段可能对不上或只是某个时点的快照，绝不能当原子指标的来源。原子指标的来源表确定后要写进指标字典并锁定，后续如需换源必须走变更流程，不能临时改。

## 派生指标

派生指标由原子指标经运算得到，须显式声明分子、分母及其口径，禁止含糊。

1. 结构声明：派生指标必须写清"分子 / 分母"或"原子 A ± 原子 B"的结构。
2. 口径对齐：分子分母必须来自同一时间范围、同一维度，口径不一致禁止相除。
3. 典型派生：退款率、客单价、签收率、件单价均为派生指标。
4. 不落错层：派生比率不宜在明细层提前算死，应在 `dws_`、`ads_` 层或查询时计算。
5. 示例：客单价 = 支付金额 / 支付订单数，可基于 `ads_trade_gmv_daily` 的原子度量派生。

派生指标最容易出错的地方是分子分母错配。例如退款率的分母应为对应口径的订单数，若分子取某月退款、分母取另一范围的订单，比率就失真。声明结构的作用就是逼着开发者把分子分母摆到台面上核对。

## 计算规则的写法

计算规则是指标的权威定义，必须写成可复现的口径描述，让数据智能体照着就能生成正确 SQL。

1. 写明来源表：规则第一句点明取自哪张有效表，例如取自 `dws_lgs_carrier_ship` 家族。
2. 写明事件与日期：注明统计哪个业务事件、按哪个业务日期归属，如 `order_date`、`pay_date`。
3. 写明过滤：把 `WHERE` 条件写进规则，例如是否只统计已支付、已签收。
4. 写明聚合：注明是 `COUNT` 还是 `SUM`，计数是否 `DISTINCT`。
5. 禁用口语：规则里不得出现"大概""差不多"之类模糊表述。
6. 字段反引号：规则中引用字段用反引号，例如 `is_paid`、`refund_rate`。

计算规则是口径的唯一事实来源。规则写得含糊，每个人读出不同口径，数就对不上。写规则时把来源表、事件、日期、过滤、聚合五要素逐一写全，是硬要求，不是建议。

## 可加和与不可加和

可加和性是指标最重要的属性之一，直接决定能不能 `SUM`，开发时必须明确标注。

1. 可加和：计数、金额类度量通常可加和，允许跨维度、跨行求和。
2. 不可加和：比率（`_rate`）、平均值（`avg_`）、去重计数（如去重访客数）不可直接相加。
3. 比率重算：汇总不可加和的比率，必须拿分子分母分别求和后再相除。
4. 去重不叠加：去重访客数这类指标不能跨天相加，需回到明细重新去重。
5. 标注上线：每个指标上线时必须在元数据里标清"可加和 / 不可加和"。

举个反例：把退款率逐月相加再除以月份数，得到的不是真实区间退款率。正确做法是把各月退款订单数与订单数分别相加，再用总分子除总分母。可加和性标注清楚，数据智能体才知道何时 `SUM`、何时重算。再看去重：去重访客数把每天的加起来当一周，会把跨天重复访问的人重复计数，必须回明细按周重新去重。可加和性不是可选说明，而是每个指标的必填属性；标注错了，哪怕规则写得再细，下游一个 `SUM` 就把口径算歪。开发时宁可多花一分钟确认，也不要留空让使用方猜。

## 时间归属

时间归属规定一条记录算在哪一天，必须区分分区日期与业务日期，这是口径准确的前提。

1. 分区用 `dt`：`dt` 是分区日期，只用于圈定扫描范围，不代表业务发生时间。
2. 业务日期专用：业务归属用 `order_date`、`pay_date` 等专用字段，不同指标归属字段可能不同。
3. 一指标一归属：每个指标必须声明唯一的时间归属字段，禁止一会按 `dt`、一会按业务日期。
4. 月报用月字段：`ads_` 月报按报告月归属，例如月报表用 `stat_month`，不要在月报上用 `dt` 当报告期。
5. 口径注明：退款等跨周期事件要写清按发生日还是完成日归属。

时间归属错是最隐蔽的口径问题。按 `dt` 统计会把补数、回刷造成的分区错位算进来。规则里务必写死："圈范围用 `dt`，算业务按业务日期"，月报则认 `stat_month`。同一事件不同指标的归属也可能不同：下单金额按 `order_date`，支付金额按 `pay_date`，两者落在不同天很常见。退款这种跨周期事件要特别写清按发生日还是完成日，否则按发生日和按完成日算出的退款率对不上，谁都解释不了差在哪。归属字段一经声明就写进指标字典，和可加和性一样作为必填项，评审时逐项核对。

## 指标命名

指标命名要让名字自带口径线索，看字段名即可判断类型与可加和性。

1. 计数用 `_cnt` 结尾。
2. 金额用 `_amount` 或 `_amt` 结尾，同表内保持一致。
3. 比率用 `_rate` 结尾，天然不可加和。
4. 平均值用 `avg_` 开头，天然不可加和。
5. 布尔用 `is_` 开头，例如 `is_paid`。
6. 小写蛇形：一律小写加下划线，禁止驼峰、中文、拼音首字母。
7. 复用词根：同义指标全库统一一种写法，禁止 `cnt` 与 `count` 混用。

命名是口径的"快捷标签"。看到 `refund_rate` 就知道是比率、不可加和；看到带 `_cnt` 的就知道是计数、多数可加和。数据智能体正是靠这套约定决定聚合方式，命名含糊会直接导致算错。还要防一类历史坑：备份表和个人副本里的字段名常和正表对不上，例如 `u_chenqi_coupon_receive_analysis` 这类副本的列可能被改名或删减，指标口径只认正表字段，副本字段不作数。新建指标字段前，先在同域有效表里查有没有同义字段，优先复用已有命名，保证同一业务含义全库只有一种写法。

## 指标上线流程

指标上线流程确保新指标在发布前完成定义、评审与验证，禁止"先上线后补口径"。

1. 登记：填写指标名、中文名、分类（原子 / 派生）、来源有效表、事件、时间归属字段、可加和性。
2. 写规则：按"计算规则的写法"写全五要素，附一段可执行的示例 SQL。
3. 评审：评审人核对口径唯一性、来源是否为正表、时间归属是否明确、可加和标注是否正确。
4. 验证：用示例 SQL 跑出非空结果，并与已有口径交叉核对，确认数对得上。
5. 发布：通过后写入指标字典，关联对应报表表，如 `ads_` 相关月报。

上线流程的底线是口径可追溯。每个对外指标都要能回答"来自哪张表、按哪天归属、能不能加"。答不上就不许上线。前置评审比上线后救火便宜得多。

## 指标变更流程

指标变更流程管理口径调整，核心是"先评估影响、再改、后通知"，禁止静默改口径。

1. 提单：写明要改的指标、现口径、新口径、变更原因与生效日期。
2. 影响评估：列出依赖该指标的报表与下游，例如引用它的 `ads_` 月报与 `dws_` 汇总。
3. 评审：确认新口径仍满足命名与可加和规范，确认历史数据是否需要回刷。
4. 并行验证：新旧口径并行跑一段，对比差异并记录原因。
5. 通知生效：按生效日期切换，提前通知所有下游使用方，更新指标字典。

变更最大的风险是下游不知情。某个比率口径一改，所有引用它的报表数都会变。影响评估和提前通知就是为了避免下游在不知情下拿到"看起来突变"的数。所有变更留痕，便于回溯对比。

## 指标下线

指标下线规定废弃指标的退出方式，核心是"先停新用、后清历史、留痕可查"。

1. 标记废弃：先在指标字典标为废弃，注明替代指标与下线日期。
2. 断引用：确认无生产报表再引用该指标，存量引用限期迁移到替代指标。
3. 隔离旧物：相关旧版本表以 `_old` 隔离，例如 `dwd_item_review_di_old`、`dwd_trade_pay_di_old`，停止写入。
4. 清理噪声：下线产生的备份、临时产物按保留策略限期清理，不得长期堆积成噪声。
5. 留档：保留下线记录与最后口径，便于历史数据追溯。

下线不是删掉就完事。要先确认没有生产链路还在用，再逐步清理。旧版本改名加 `_old` 是为了明确标识退役，提醒任何人都不要再引用。留档则保证历史报表的口径日后仍可解释。
