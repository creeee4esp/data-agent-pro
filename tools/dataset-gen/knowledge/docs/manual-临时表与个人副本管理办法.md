# 临时表与个人副本管理办法

本办法管理仓库里除 123 张有效表之外的各类非正式表，重点是临时表、个人副本、备份表、分表与测试表。这几类加起来构成了 3175 张噪声表的主体，是取数时最容易误选的对象，本办法给出命名、创建、使用与清理的硬性要求。

## 适用对象

本办法适用于所有会在仓库里建表的人员：数据工程、数据分析师，以及代其创建个人副本的工具，面向的表是以 `tmp_`、`u_<用户>_`、`test_` 开头，或带 `_bak`、`_his`、`_old`、纯日期后缀的非正式表。

1. 数据分析师做临时取数时建的 `tmp_*`（如 `tmp_channel_monthly_0407`）和个人副本 `u_<用户>_*`（如 `u_chenqi_coupon_di_analysis`）都在管辖范围内。
2. 数据工程发布前后产生的备份（`ads_pay_channel_monthly_bak`）、带日期备份（`ads_item_review_score_monthly_bak_20250221`）、旧版本（`dwd_item_review_di_old`）同样受本办法约束。
3. 正式有效表（五层前缀下的 123 张）不属于本办法，按《数据开发上线流程》管理。
4. 任何人取数时，只要命中上述非正式表，都应先按本办法判断能不能用。

取数例子：想统计 3 月渠道支付，看到 `u_chenqi_channel_monthly_tmp` 不要直接用，应改读有效表 `ads_pay_channel_monthly` 并按 `dt` 筛 3 月。

## 命名要求

命名要求约束非正式表的前缀与后缀，命名不合规的非正式表一经发现限期改名或清理。

1. 临时表必须以 `tmp_` 开头，格式形如 `tmp_<内容>_<日期或批次>`，例如 `tmp_aftersale_order_0221`、`tmp_category_di_1226`。
2. 个人副本必须以 `u_<用户>_` 开头，带上本人标识，例如 `u_chenqi_coupon_receive_analysis`，便于一眼看出归属。
3. 备份表用 `_bak` 或 `_bak_<日期>` 后缀，历史归档用 `_his`，旧版本用 `_old`，不得混用，例如 `ads_trade_gmv_monthly_his`、`ads_lgs_delivery_monthly_bak_20250217`。
4. 严禁给非正式表起成正式表的样子。把临时结果命名成 `ads_pay_channel_monthly` 这类正式表的名字会污染有效表清单，这是明令禁止的。

取数例子：看到 `item_review_202301`（月分表）或 `item_review_20250101`（日分表），应回到有效表按 `dt` 分区取，不要直接查分表。

## 创建审批

创建审批区分"随手建"和"要留痕"两类，个人临时用途免审批但限时，长期或共享用途须走审批。

1. 个人副本 `u_<用户>_*` 和临时表 `tmp_*` 供本人短期分析用，免审批即可创建，但须接受生命周期约束。
2. 发布相关的备份表（如 `ads_lgs_delivery_monthly_bak`）由数据工程在发布流程内创建，须登记用途与保留期限，不允许随手留。
3. 任何要被他人或下游任务读取的表都不能走免审批路径，必须按《数据开发上线流程》建成有效表。
4. 测试表 `test_*` 只在验证环节临时建，用途单一，不得长期留存。

取数例子：临时核对优惠券领取，建 `u_chenqi_coupon_receive_analysis` 自用可以；但若要给他人出结论，就得基于有效表 `ads_coupon_usage_monthly` 另建正式产出。

## 使用范围

使用范围限定非正式表只能自用、只在当前分析里用，禁止进入任何对外产出链路。

1. 个人副本只有创建者可用，不对外共享；`u_chenqi_coupon_di_analysis` 只服务于 chenqi 本人的当次分析。
2. 临时表 `tmp_*` 只在当次取数脚本内使用，用完即弃，不作为其他脚本的上游。
3. 备份、历史归档、旧版本、分表、测试表一律不得作为报表、看板、调度任务或数据智能体的数据来源。
4. 对外需要的数字一律回到有效表取。

取数例子：要出 GMV 看板，数据来源必须是 `ads_trade_gmv_daily`，不能图省事读 `ads_trade_gmv_monthly_his` 或 `test_ads_trade_cate1_sales_monthly`。

## 生命周期

生命周期规定各类非正式表的默认存活时长，到期即视为可清理对象，责任人不得指望其长期存在。

1. 临时表 `tmp_*` 为最短生命周期，默认当次分析结束即清理；像 `tmp_channel_monthly_0407` 这种带日期名的，日期之后就应消失。
2. 个人副本 `u_<用户>_*` 为中短期，随本人分析任务结束而清理，不随账号长期累积，当前已有 345 张，说明积压明显。
3. 备份与带日期备份有明确保留期，过期即清理，`ads_item_review_score_monthly_bak_20250221` 这类不应长期占用存储。
4. 旧版本 `_old`、历史归档 `_his`、分表（月分表 216 张、日分表 1825 张）按归档策略统一到期处理。

取数例子：发现自己名下有半年前的 `u_chenqi_channel_monthly_tmp`，应主动删除，需要长期用就申请沉淀为有效表。

## 定期清理

定期清理是对到期非正式表的集中治理，清理按类型分批执行，清理前通知责任人。

1. 清理覆盖全部噪声类型：历史归档 13 张、备份 98 张、带日期备份 510 张、测试表 58 张、旧版本 44 张、月分表 216 张、日分表 1825 张、临时表 66 张、个人副本 345 张，合计构成 3175 张的主要来源。
2. 带日期后缀的表优先清理，`ads_trade_cate1_sales_monthly_bak_20250309`、`lgs_shipment_20250101` 这类日期已过的最先回收。
3. 清理前核对血缘，确认没有生产任务在读；若发现有任务依赖噪声表，先推动迁移到有效表再清理。
4. 清理动作留痕，记录被删表名与时间，便于追溯。

取数例子：清理前扫描到某任务在读 `ads_lgs_delivery_monthly_bak`，正确处理是把它改读有效表 `ads_lgs_delivery_monthly`，再回收备份表。

## 备份表管理

备份表管理针对 `_bak`、`_bak_<日期>`、`_his` 三类，明确它们只为回滚与归档服务，不是对外口径。

1. 备份表仅在发布或变更前后短期保留，`ads_pay_channel_monthly_bak` 用于必要时回滚，用完按保留期清理。
2. 带日期备份（510 张）记录某一时点快照，如 `ads_item_review_score_monthly_bak_20250221`，不得当成"该月正式数据"对外引用。
3. 历史归档 `_his`（13 张，如 `dim_user_his`、`ads_trade_gmv_monthly_his`）供历史回溯，访问须有明确归档用途。
4. 严禁把备份表接入报表或调度，任何长期依赖备份表的链路都要整改。

取数例子：要看 2 月 21 日的评分，不要直接查 `ads_item_review_score_monthly_bak_20250221`，而是查有效表 `ads_item_review_score_monthly` 对应 `dt`。

## 分表管理

分表管理针对按月、按日拆开的历史分表，明确它们是遗留结构，取数应优先走有效表的 `dt` 分区。

1. 月分表（216 张，如 `item_review_202301`、`lgs_shipment_202301`、`log_visit_202301`）按月份拆名，不属于有效表清单。
2. 日分表（1825 张，如 `item_review_20250101`、`lgs_shipment_20250101`、`log_visit_20250101`）数量最大，是噪声表里的大头。
3. 需要某段时间数据时，用有效表加 `dt` 分区过滤，而不是逐个拼接分表；业务时间按 `order_date` / `pay_date` 过滤。
4. 分表按归档策略集中清理，不再新增新的日期分表。

取数例子：统计 2025 年 1 月 1 日访问量，不要查 `log_visit_20250101`，应查对应有效表并限定 `dt = '20250101'`。

## 测试表管理

测试表管理针对 `test_*`，明确它们只服务验证环节，结果不具备生产口径效力。

1. 测试表（58 张，如 `test_ads_item_review_score_monthly`、`test_ads_pay_channel_monthly`、`test_ads_trade_cate1_sales_monthly`）只在数据验证期临时存在。
2. 测试表数据可能是样本或造数，不能用于任何对外结论或对账基准。
3. 验证结束后测试表随即清理，不得遗留；长期存在的 `test_*` 一律按违规清理。
4. 禁止把测试表当成正式表的替身接入看板或调度。

取数例子：看到 `test_ads_trade_cate1_sales_monthly` 想直接出销售结论是错误做法，应改用有效表 `ads_trade_cate1_sales_monthly`。

## 违规处理

违规处理针对把非正式表用作生产来源、超期不清理、冒充正式表命名等行为，按影响分级处置。

1. 一般违规（如超期保留 `tmp_*`、个人副本积压）通报并限期自清。
2. 严重违规（把 `u_chenqi_coupon_di_analysis` 等个人副本或 `ads_pay_channel_monthly_bak` 等备份表接入报表、调度或数据智能体）立即断开依赖并整改。
3. 用测试表、旧版本表（`dwd_trade_pay_di_old`、`ads_trade_refund_rate_monthly_old`）对外出结论的，按数据事故复盘。
4. 把非正式结果命名成正式表样子污染有效表清单的，强制改名或清理并追责。

取数例子：若发现有看板读取 `ads_trade_gmv_monthly_his`，先把数据源切回有效表 `ads_trade_gmv_daily`（按 `dt` 汇总），再对相关责任人通报处理。
