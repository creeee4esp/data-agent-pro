# SQL 编写规范

## 基本格式

SQL 语句的书写格式要统一，目的是让别人、也让自动写 SQL 的数据智能体一眼看懂你在取什么数、从哪张表取、按什么条件过滤。

1. 关键字大写、表名字段名小写，例如 `SELECT`、`FROM`、`WHERE` 大写，`dws_trade_prov_order_1d`、`order_date` 小写。
2. 每个被 `SELECT` 的字段单独一行，`FROM`、`JOIN`、`WHERE`、`GROUP BY`、`ORDER BY` 各自另起一行，层次清楚。
3. 表名、字段名一律用反引号包裹，例如 `dws_trade_brand_order`、`is_paid`、`refund_rate`，避免与保留字冲突。
4. 复杂逻辑用 CTE（`WITH`）拆成几段，每段只做一件事，不要把十层嵌套塞进一条语句。
5. 给每张表起有意义的别名，不要用 a、b、c 这种无信息的字母。

把格式做规整不是为了好看。当一个月报出了问题，别人翻开你的 SQL 要能在十秒内看明白你用的是 `ads_trade_gmv_daily` 还是别的表、过滤的是哪一天。格式混乱的 SQL，哪怕逻辑对，维护起来也是负担。写完先自己从上往下读一遍，读不顺就说明还能再拆。

## 选表优先级

选表是写 SQL 的第一步，也是最容易翻车的一步，因为库里有 123 张有效表，却有 3175 张噪声表，名字长得又像。

选表时按这个优先级来：

1. 要固定报告期的结论，优先用 `ads_` 报表层，例如按月的 GMV 口径就从 `ads_trade_gmv_daily` 聚合，或用对应月报表。
2. 要灵活时间范围或多维下钻，用 `dws_` 汇总层，并按粒度选 `1d`、`1w`、`1m`，例如省份日粒度用 `dws_trade_prov_order_1d`。
3. 要最细明细或自定义口径，才回 `dwd_` 明细层。
4. 任何情况下都只能用有效表，禁止用噪声表。

最关键的一条是识别并避开噪声表。看到 `ads_item_review_score_monthly_bak`、`ads_pay_channel_monthly_bak` 这种 `_bak` 结尾的，是备份，共 98 张，不要用；看到 `ads_trade_cate1_sales_monthly_bak_20250309` 这种带日期的，是带日期备份，共 510 张，不要用；看到 `test_ads_pay_channel_monthly` 这种 `test_` 开头的，是测试表，共 58 张，不要用。它们可能缺列、列名被改，或者只装了某个时点的快照，拿来出数就会错。记住一句话：统计一律用正表。

## 关联写法

表与表关联时，写法要显式、可控，别让 `JOIN` 悄悄把行数放大或缩小。

1. 一律用显式 `JOIN ... ON`，禁止用逗号加 `WHERE` 的隐式关联写法。
2. 关联键要能保证粒度不变，关联前先想清楚左右两张表各是什么粒度，`JOIN` 后一行代表什么。
3. 关联维度时只关联当前生效的维表，禁止关联 `dim_user_his` 这类历史归档维表，否则会把过期维度带进来。
4. 多表关联时逐个加表、逐步验证行数，不要一口气 `JOIN` 五张表再回头找为什么行数翻倍。
5. 关联用的键字段用反引号写清楚，例如 `ON a.order_id = b.order_id`。

关联最常见的坑是一对多导致的重复放大。比如把一张订单表和一张明细表关联后再算订单数，订单会被明细行数重复计数。遇到这种情况，要么先把其中一张聚合到一致粒度再关联，要么在计数时用 `DISTINCT`。关联写完，务必对一下关联前后的行数是否符合预期。

## 去重计数

去重计数要格外小心，因为去重后的结果天然不可加和，很多口径错误都出在这里。

1. 统计去重的订单数、买家数、访客数，必须用 `COUNT(DISTINCT 字段)`，不能用 `COUNT(*)`。
2. 去重计数结果不可跨行、跨天相加。例如去重访客数不能把每天的加起来当作一周的，要回明细按周重新去重。
3. 关联放大后再去重时，`DISTINCT` 要作用在真正唯一的业务键上，例如 `COUNT(DISTINCT order_id)`。
4. 带条件的去重计数，把条件写进 `IF` 或 `CASE`，例如只数已支付订单时按 `is_paid` 过滤。
5. 别把可加和与不可加和混在一个 `SUM` 里，去重类单独算。

举个具体场景：算某家族的支付订单数，如果用的是日表 `dws_trade_prov_order_1d`，把每天的去重订单数直接相加会重复计数跨天下单的情形。正确做法是回到明细按整个区间一次性去重，或使用已经按区间口径算好的汇总。去重计数的铁律就一句：先想清楚唯一键，再决定能不能加。

## 比率与平均值

比率和平均值是派生指标，写 SQL 时绝不能把它们当普通数字直接平均或相加。

1. 汇总比率（`_rate` 结尾，如 `refund_rate`）必须拿分子分母分别 `SUM` 后再相除，禁止对比率列直接求平均。
2. 平均值（`avg_` 开头，如平均评分、平均时长）同理，要用加权方式还原，不能把各行的平均值再平均一次。
3. 分子分母必须同口径、同时间范围、同维度，不能分子取一个范围、分母取另一个范围。
4. 相除前处理分母为零，用 `NULLIF` 或 `CASE` 避免除零报错。
5. 比率结果的小数位按口径约定保留，不要随意四舍五入改变精度。

一个典型错误是算区间平均评分时，把每天的平均分加起来除以天数。评价条数多的那天权重应该更大，直接平均会失真。正确写法是把评分乘以评价数后 `SUM`，再除以评价数之和。比率与平均值这一类，心里要始终清楚它们不可加和，所有汇总都得回到分子分母。

## 日期处理

日期处理要分清分区日期和业务日期，这决定了你圈的是对的数据、算的是对的口径。

1. 分区字段 `dt` 只用于圈定要扫描的分区范围，缩小扫描量，不代表业务发生时间。
2. 业务归属用专用字段，例如下单按 `order_date`、支付按 `pay_date`，统计业务指标必须用业务日期过滤。
3. `ads_` 月报按报告月取数，例如月报表用 `stat_month`，不要在月报表上拿 `dt` 当报告期去过滤。
4. 日期范围过滤写成左闭右开或明确的闭区间，表达清楚边界，避免漏算或多算一天。
5. 别把字符串日期和日期字段隐式比较，格式不一致会悄悄过滤错。

最容易犯的错是图省事，所有过滤都写在 `dt` 上。按 `dt` 统计 GMV，会把补数、回刷造成的分区错位算进来，口径就不准了。正确姿势是：圈范围、减扫描用 `dt`，算业务指标按 `order_date` 或 `pay_date`，月报则认 `stat_month`。写日期条件前，先确认这张表到底有哪些日期字段，别凭印象套。

## 空值处理

空值处理要有明确策略，`NULL` 在聚合、关联、比较里的行为和普通值不同，处理不当就会悄悄算错。

1. 聚合前想清楚 `NULL` 的含义，是"没有"还是"未知"，不同含义处理方式不同。
2. 计数时注意 `COUNT(字段)` 会跳过 `NULL`，`COUNT(*)` 不会，按口径选对写法。
3. 条件判断布尔字段时显式写等值，例如 `is_paid = 1`，不要依赖字段是否为真的隐式判断。
4. 除法分母可能为空或零时，用 `NULLIF` 或 `COALESCE` 兜底，避免结果变成 `NULL` 或报错。
5. 关联键可能为 `NULL` 时，`JOIN` 会丢行，必要时用 `LEFT JOIN` 并对结果的 `NULL` 做 `COALESCE`。

空值问题的隐蔽之处在于它不报错，只是默默让结果偏小。比如用某字段计数，如果该字段有一批 `NULL`，`COUNT(字段)` 会比实际记录数少。处理空值的原则是：先弄清每个可能为空的字段代表什么，再决定是过滤、填默认值，还是保留。不要一律 `COALESCE` 成 0 了事。

## 性能注意

性能问题多数来自没有利用分区和一次扫太多数据，写 SQL 时顺手就能避开大半。

1. 一定要带分区过滤，用 `dt` 把扫描范围限定在需要的天数内，不要全表扫 123 张有效表里数据量最大的那几张。
2. 只 `SELECT` 需要的列，禁止无脑 `SELECT *`，尤其是宽表和多表关联时。
3. 能用已算好的汇总就不要从明细现算，例如按月 GMV 优先用 `ads_trade_gmv_daily` 聚合，而不是每次从明细重算。
4. 大表关联前先各自过滤、聚合到小结果再 `JOIN`，减少参与关联的数据量。
5. 用 CTE 或临时结果复用中间计算，避免同一段逻辑在一条语句里算好几遍。

性能好不好，先看有没有吃到分区。一条没有 `dt` 过滤的查询，哪怕逻辑对，也可能把全历史的数据都扫一遍，又慢又占资源。选表时优先用高层级的汇总表，也是性能考虑：汇总层把常用聚合固化了，直接取比从明细现算快得多。写完大查询，先估一下大概要扫多少数据，心里有数再提交。

## 禁止事项

有几类写法是明令禁止的，踩到任意一条，评审直接打回，不论结果数对不对。

1. 禁止用噪声表出口径，包括 `_his`（如 `ads_coupon_usage_monthly_his`、`dim_user_his`）、`_bak`、`_bak_日期`、`_old`（如 `ads_trade_refund_rate_monthly_old`）、`test_`、`tmp_`（如 `tmp_channel_monthly_0407`）、`u_`（如 `u_chenqi_coupon_di_analysis`）以及无前缀的月分表、日分表。
2. 禁止越级取数，例如 `ads_` 结论直接 FROM `ods_` 表，必须经 `dws_`、`dwd_` 沉淀。
3. 禁止对比率列（`_rate`）和平均值列（`avg_`）直接 `SUM` 或求平均。
4. 禁止把去重计数结果跨天、跨行相加。
5. 禁止用 `dt` 代替业务日期做业务归属。
6. 禁止隐式关联（逗号加 `WHERE`）和无条件的 `SELECT *`。

这几条之所以是红线，是因为它们都会在不报错的情况下产出错误的数。错误的数比报错更危险——报错会被发现，错数会被当成事实用出去。写完 SQL，对照这份禁止清单过一遍，比事后被业务追着问"这个数怎么对不上"要省事得多。

## 示例评审清单

示例评审清单是提交 SQL 前的自检表，逐条打勾再提交，能挡掉绝大多数口径事故。

1. 选表：用的是不是有效表，有没有误用 `_bak`、`_old`、`test_`、`tmp_`、`u_` 或分表。
2. 分层：有没有越级，`ads_` 结论是不是经由 `dws_`、`dwd_` 取数。
3. 关联：`JOIN` 是不是显式写法，关联后行数是否符合预期，有没有一对多放大。
4. 维度：关联的是不是当前维表，有没有误连 `dim_user_his` 这类历史归档。
5. 去重：该去重的地方是不是用了 `COUNT(DISTINCT ...)`，去重结果有没有被错误相加。
6. 比率：`_rate`、`avg_` 是不是用分子分母重算，分母有没有防零。
7. 日期：业务指标是不是按 `order_date`、`pay_date` 归属，`dt` 只用于圈范围，月报是不是认 `stat_month`。
8. 空值：可能为空的字段有没有明确处理策略。
9. 性能：有没有带 `dt` 过滤，有没有 `SELECT *`。
10. 结果：跑出来是不是非空、是不是和已有口径对得上。

这份清单建议真的逐条看，而不是扫一眼。很多问题单看逻辑发现不了，必须对着清单一项项核。把自检做在前面，评审人就能把精力放在更深的口径讨论上，整个团队的取数质量才会稳步往上走。
