# 数据开发上线流程

本流程规范从需求到上线后观察的全链路，适用于 `ods_`、`dim_`、`dwd_`、`dws_`、`ads_` 五层有效表的新增与变更。仓库当前有效表 123 张，噪声表 3175 张，流程的一个核心目标就是不让新开发再往 3175 张里增加垃圾，每一张新表都必须按本流程走完并落在五层前缀之内。

## 需求评审

需求评审的对象是一份明确到指标与产出表的取数或建模需求，评审通过后才允许进入设计，口头需求不予立项。

1. 需求方须写清目标指标、产出表候选名、更新周期与使用场景，例如"按渠道出月度支付汇总，产出 `ads_pay_channel_monthly`，月更"。
2. 评审先查重：如果已有有效表能满足（如 `ads_trade_gmv_daily`、`ads_trade_cate1_sales_monthly`），直接复用，不新建表。
3. 评审要判断粒度与周期，确认该落在哪一层。明细需求进 `dwd_`，汇总需求进 `dws_`，成品报表进 `ads_`。
4. 评审结论记录在案，含产出表名、负责人与预期上线时间，作为后续各环节的基线。
5. 评审还要确认数据量级与存储预算，明确是全量回溯还是仅增量，避免上线后才发现要回刷多年历史分区而拖垮资源。
6. 对跨域需求（如同时涉及交易与物流），评审要指定主责域，防止两边各建一张口径相近的表，重蹈 3175 张噪声表的覆辙。

容易误用的一点：别把"临时看一眼"当成需求立项。临时分析应走个人副本 `u_<用户>_*` 或临时表 `tmp_*`，只有要长期复用、要进调度的才立项建正式表。

## 模型设计

模型设计产出表结构与命名方案，设计须明确表名、分层、分区与字段，命名不合规的设计不予通过。

1. 命名必须带正确分层前缀。汇总层遵循 `dws_<域>_<粒度>_<事件>_<周期>`，周期取 `1d` / `1w` / `1m`，例如 `dws_trade_prov_order_1d`；设计评审会对照 `dws_trade_brand_order`、`dws_lgs_prov_ship` 等现有家族确认风格一致。
2. 所有表以 `dt` 作为分区字段，业务日期用 `order_date` / `pay_date` 等单独字段表达，设计时须把 `dt` 与业务日期分开，不得混用。
3. 字段须复用公共维度（如 `dim_` 维度），避免每张表各自造键；含敏感字段的要在设计阶段标出。
4. 禁止把临时命名带进设计。设计稿里出现 `tmp_channel_monthly_0407` 这类名字直接退回，正式表不允许带日期或 `tmp_` 后缀。
5. 设计要明确周期语义并与家族对齐。物流域已有 `dws_lgs_carrier_ship`、`dws_lgs_warehouse_ship`，评论域已有 `dws_item_brand_review`、`dws_item_cate1_review`、`dws_item_sku_review`，新表的域、粒度、事件命名要与同族保持一致，避免同一事件出现两套叫法。
6. 分区与回溯策略在设计阶段就要定：按 `dt` 分区存储，声明保留多少历史分区、是否需要初始化回刷，防止上线后临时拍脑袋。

容易误用的一点：`_monthly` 是 `ads_` 成品的习惯后缀（如 `ads_coupon_usage_monthly`），但 `dws_` 要用 `1m` 表达月周期，两套写法不要混。

## 开发与自测

开发与自测阶段产出可运行的加工脚本与自测结果，自测在开发分支或个人空间完成，不得污染正式表。

1. 开发中间结果写到个人副本 `u_<用户>_*` 或临时表 `tmp_*`，例如 `u_chenqi_channel_monthly_tmp`，不要直接写目标 `ads_` 表。
2. 自测至少覆盖：分区是否按 `dt` 正确切分、业务日期字段（如 `pay_date`）是否对齐、金额类指标与已有口径（如 `ads_trade_gmv_daily`）是否能对上。
3. 自测数据量要足够，至少跑通一个完整周期；月更表要验证跨月切换，日更表要验证连续多个 `dt`。
4. 自测通过后清理本次产生的 `tmp_*` 中间表，不要留给后续环节。
5. 自测要覆盖边界分区：首个 `dt`、空数据 `dt`、补数重跑同一 `dt` 时是否幂等（重跑不应产生重复行），这些是日更表最容易出问题的地方。
6. 开发阶段的个人副本随手起名也要规范。自测用的 `u_chenqi_coupon_receive_analysis` 这类表只服务本次开发，不要让它被别的脚本引用，更不能作为下游上游。

容易误用的一点：别拿备份表或旧版本表做基准对数。`ads_item_review_score_monthly_bak`、`dwd_trade_pay_di_old` 都不是现行口径，用它们对出来的"一致"没有意义。

## 代码评审

代码评审针对加工脚本本身，评审聚焦口径正确与来源合规，有未解决评审意见的代码不得进入数据验证。

1. 评审检查数据来源是否全部为有效表。脚本若读取 `*_bak`、`*_his`、`*_old`、`test_*`、`tmp_*` 或 `u_<用户>_*`，一律打回，例如读取 `u_chenqi_coupon_di_analysis` 作为上游属于严重问题。
2. 评审确认分区过滤写法正确，取数按 `dt` 过滤，业务时间按 `order_date` / `pay_date` 过滤，二者不混用。
3. 评审核对命名与目标设计一致，产出表名与模型设计一致，不得临时改名。
4. 评审意见须逐条闭环，重大口径问题要求重测。

容易误用的一点：全表扫描是高频问题。缺少 `dt` 过滤的查询会扫全历史分区，评审要特别盯住这类写法。

## 数据验证

数据验证在预发或受控环境核对产出结果，验证通过是上线的前置条件，验证不通过不得配置调度。

1. 验证产出表的行数、分区覆盖与关键指标，确认每个 `dt` 分区都有数据且无重复。
2. 做口径交叉对账：新表 `dws_trade_cate1_order` 的汇总应能与上游明细对上，`ads_` 成品应能与同口径现有报表对齐。
3. 验证金额、数量等核心指标的量级合理，发现突变要定位是数据问题还是口径问题。
4. 验证结论留档，含对账结果与样本，作为后续回滚判断的参照。
5. 验证要做唯一性与完整性检查：同一 `dt` 内主键不重复、关键维度（如品牌、类目、省份）取值落在 `dim_` 维度范围内，避免出现脏维度。对 `dws_trade_brand_order`、`dws_trade_cate1_order` 这类带维度的汇总尤其要查。
6. 验证金额与上游明细对账时，要用相同的业务时间口径。按 `pay_date` 聚合的结果只能和同样按 `pay_date` 的上游比，不能一边用 `pay_date` 一边用 `dt`，否则看似差异其实是口径错配。

容易误用的一点：别只验证一天就上线。日更表要连续验证多个 `dt`，月更表（如 `ads_lgs_delivery_monthly`）至少验证一个完整自然月。

## 调度配置

调度配置把通过验证的脚本接入定时任务，调度须声明依赖与周期，缺依赖或周期错配的任务不予上线。

1. 调度周期与表周期一致：日更表按日调度，月更表按月调度；`dws_` 的 `1d` / `1w` / `1m` 周期要与调度频率匹配。
2. 上游依赖显式声明，下游任务等上游 `dt` 分区就绪再触发，禁止靠时间点"估着跑"。
3. 调度对象只能是有效表任务，禁止把一次性的 `tmp_*` 脚本挂进常驻调度。
4. 配置失败重试与告警，核心表（如 `ads_trade_gmv_daily`）要设置分区缺失告警。

容易误用的一点：依赖漏声明会导致空跑。若 `ads_pay_channel_monthly` 不等上游明细就绪就启动，会产出一个"看着成功、其实缺数"的分区。

## 上线发布

上线发布把表与调度正式切到生产，发布须按清单执行，未走完前序环节的不得发布。

1. 发布前核对清单：模型设计、代码评审、数据验证、调度配置均已通过，产出表名合规且落在五层前缀内。
2. 发布时建正式表并授予必要权限，首个生产 `dt` 分区跑通后才对下游与使用方开放。
3. 发布即登记到有效表清单，使有效表总数变化可追溯；禁止"先建着不登记"。
4. 发布窗口避开高峰与月初月末对账期，重大表发布需提前知会使用方。

容易误用的一点：别用手工导数"先顶上"。手工往生产表塞数据会和调度产出冲突，正确做法是让调度产出第一个 `dt` 分区。

## 回滚方案

回滚方案规定上线出问题时如何快速恢复，方案须在发布前准备好，没有回滚方案不允许上线。

1. 发布前为受影响表保留可回滚的快照或分区，回滚目标明确到具体 `dt`。
2. 回滚优先按分区回退：坏数据只影响个别 `dt` 时，重跑或清理该分区，不整表推倒。
3. 若必须用备份恢复，使用规范的发布前快照，而不是随手留下的 `ads_lgs_delivery_monthly_bak` 这类来历不明的备份表。
4. 回滚后要重新跑一遍数据验证，确认恢复到的口径与上线前一致。

容易误用的一点：带日期备份表不是回滚依据。`ads_trade_cate1_sales_monthly_bak_20250309` 只是某人某天随手留的，不保证完整，正式回滚要用发布流程登记的快照。

## 上线公告

上线公告面向数据使用方与数据智能体，公告须写清新表名、口径、周期与生效 `dt`，避免使用方继续用旧表或噪声表。

1. 公告列明新上线的有效表名及用途，例如新增 `dws_trade_prov_order_1d`，说明域、粒度、事件与周期。
2. 若新表替代了旧产出，明确旧表停用计划，引导使用方从 `*_old`（如 `ads_trade_refund_rate_monthly_old`）切到新表。
3. 公告注明首个可用 `dt` 分区与历史回溯范围，避免使用方查到无数据的分区。
4. 公告同步给数据智能体的可选表清单，使其在 123 张有效表内选表。

容易误用的一点：公告别只发给人。数据智能体按表名选表，若不同步更新可选清单，它可能继续命中已停用的旧表。

## 上线后观察

上线后观察在生产运行的头几个周期持续盯产出，观察期未结束不算真正交付，异常要能及时发现。

1. 观察期至少覆盖一个完整周期：日更表连续看多个 `dt`，月更表看满一个自然月。
2. 盯指标稳定性与分区完整性，核对新表（如 `dws_lgs_warehouse_ship`）每个 `dt` 是否按时、按量产出。
3. 观察使用方与审计反馈，若发现仍有任务在读旧表或备份表，推动其迁移到新有效表。
4. 观察期结束后归档验证与观察记录，正式把表移交日常运维。

容易误用的一点：别把"调度成功"当成"数据正确"。任务状态绿不代表口径对，观察期要持续对账，尤其是和 `ads_trade_gmv_daily` 这类核心口径的交叉校验。
