# 数据质量规范

## 质量维度

数据质量从完整性、唯一性、准确性、一致性、时效性五个维度衡量，每张有效表上线时都要声明它在各维度上的检查项。

1. 完整性：关键字段非空、分区不缺失。
2. 唯一性：主键或业务粒度不重复。
3. 准确性：指标口径算得对，与来源对得上。
4. 一致性：上下游分层之间口径一致、可对账。
5. 时效性：产出按调度时间准点完成。

五个维度覆盖全库 123 张有效表的质量底线。3175 张噪声表不纳入质量监控，但要被识别隔离，防止误入分析口径。按维度拆检查项的好处是出问题时能快速定位是哪一类质量问题，再对号入座走对应的处理流程。五个维度之间并非孤立：时效延迟可能连带分区缺失进而破坏完整性，关联维表未更新会同时伤害准确性与一致性。因此每张表上线时都要把五维检查项一次性声明齐全，而不是只挑容易的做。声明时要落到具体字段和具体阈值上，例如哪些字段非空、主键是哪几列、波动阈值定多少，含糊的"保证质量"不算数。

## 主键唯一

主键唯一属于唯一性维度，确保一张表的粒度不被重复行破坏，是最基础也最高频的检查。

1. 每张有效表上线时必须声明主键或业务粒度键。
2. 唯一性检查对比"主键去重后行数"与"总行数"，不一致即重复。
3. `dws_` 汇总表按 `dws_<域>_<粒度>_<事件>_<周期>` 的粒度校验唯一，例如 `dws_trade_prov_order_1d` 按省份加日期唯一。
4. 重复最常见的成因是任务重跑前未清理当天分区，导致同一 `dt` 写入两份。
5. 检查命中重复：定位重复分区，清理后重跑，不得带病对外。

主键重复会让所有 `SUM`、`COUNT` 翻倍放大，是口径事故的高发源头。尤其重跑场景，若不先清理目标分区就追加写入，极易产生整段重复。唯一性检查要作为生产作业的前置卡点，不通过不发布。检查要落到家族里每一张表：`dws_trade_brand_order`、`dws_trade_cate1_order` 这些家族的日、周、月三张表各自的粒度键不同，不能用一套键去套所有周期表。还要注意 `ads_` 月报按 `stat_month` 加维度唯一，不是按 `dt` 唯一，校验键选错会把本该重复的误判为正常、或把正常误判为重复。

## 非空检查

非空检查属于完整性维度，防止关键字段缺值把下游口径悄悄算小。

1. 每张表声明一批"关键非空字段"，例如主键、业务日期、核心度量。
2. 非空检查统计关键字段的 `NULL` 行数，超过阈值即告警。
3. 业务日期字段必须非空，例如 `order_date`、`pay_date`，否则时间归属无从判断。
4. 关键字段突然大批量为空，常因上游业务系统字段改名，或关联维表时维表未更新。
5. 布尔类字段按口径确认允许值，例如 `is_paid` 只应为约定取值。

空值的危害在于不报错。`COUNT(字段)` 会跳过 `NULL`，结果比实际偏小却不自知。非空检查就是把这类静默偏差显性化。命中后先查上游是不是改了字段或维表没跟上，修复源头再回刷，而不是简单把 `NULL` 填成零。

## 分层对账

分层对账属于一致性维度，核心是"汇总等于明细、报表源自汇总"，保证口径在层间不走样。

1. `dws_` 汇总的可加和指标总额，必须等于对应 `dwd_` 明细聚合的总额。
2. `ads_` 报表的口径必须能追溯到 `dws_` 或 `dwd_`，禁止越级直接读 `ods_`。
3. 对账只在有效表之间进行，禁止拿 `_bak`、`_old` 等噪声表参与对账。
4. 比率、平均值等不可加和指标，对账时比对分子分母，而非直接比对比率。
5. 对账差异超阈值即告警，定位是哪一层加工引入偏差。

分层对账是发现口径漂移的主要手段。只要汇总与明细对不平，说明中间某一步加工丢数或重复。对账时要确保两边同口径、同时间范围、同维度，否则对出的"差异"本身就是假的。对账通过是汇总与报表对外发布的前提。具体执行上，可加和指标直接比对总额，例如 `dws_trade_prov_order_1d` 的订单总数应等于对应明细按同口径聚合的结果；不可加和的比率则拆成分子分母分别比对。对账还要防止把噪声表拉进来：`ads_item_review_score_monthly_bak` 这类备份表数据可能停留在某个旧时点，拿它对账只会对出一堆无意义的差异。

## 波动监控

波动监控属于准确性维度，通过和历史比较，把异常的突增突降及时拦下来。

1. 核心指标按天与前一日、前一周同日比较，波动超过约定阈值即告警。
2. 行数波动是最通用的信号，一张表行数与前一天相比大幅变化要触发核查。
3. `ads_` 报表口径波动重点盯，例如 `ads_trade_gmv_daily` 的日 GMV 异常跳变要第一时间排查。
4. 波动既可能是真实业务变化，也可能是数据质量问题，告警后须人工确认成因。
5. 大促等已知业务高峰提前标注，避免误报淹没真实告警。

波动监控的价值是"不用等业务来问就先发现"。但它只给信号、不下结论：一次突增可能是活动真实拉动，也可能是重复写入。所以告警后必须结合唯一性、对账等检查判断是真波动还是假数据，再决定是否按事故处理。阈值要分表设定，流量大、季节性强的表容忍区间宽一些，口径敏感的 `ads_` 报表收紧一些。还要把同比和环比结合看，单看环比容易被周末、节假日的正常起伏误导，叠加与上周同日的比较能滤掉一部分规律性波动，让真正的异常更突出。

## 时效监控

时效监控属于时效性维度，保证各层按调度时间准点产出，下游才能按时用数。

1. 各层有既定的调度起点，依赖上游全部成功后运行，处理前一天（T-1）的数据。
2. 时效监控盯两件事：是否启动、是否在约定时点前完成。
3. 产出延迟常见成因有上游 ODS 同步超时、集群资源不足排队、依赖任务失败后重跑。
4. 分区缺失也属时效问题，常因调度依赖配置错误导致任务被跳过，或上游当天无数据未告警。
5. 超时未产出即告警，通知对应责任团队介入。

时效问题影响面大，因为下游层层依赖。ODS 延迟会沿链路顺延到 ADS 报表，业务早上就看不到昨天的数。监控既要抓"没跑"，也要抓"跑慢了"。分区缺失尤其隐蔽，任务没报错但数据没进来，必须单独监控分区是否按时就位。

## 告警分级

告警分级按影响范围和紧急程度分级，确保严重问题优先响应，次要问题不淹没主线。

1. 一级：对外报表口径错误或核心产出缺失，影响业务决策，须立即响应。
2. 二级：重要指标波动异常或关键字段大批为空，须当日内处理。
3. 三级：非核心表延迟、轻微波动，按常规节奏处理。
4. 升级规则：二级在约定时限内未解决升为一级。
5. 分级依据：看受影响的下游数量与是否已对外发布。

分级的目的是把有限的响应精力投到最要紧的地方。一张无人依赖的边缘表晚产出，和 `ads_trade_gmv_daily` 口径出错，显然不是一个量级。告警若不分级，所有问题同等刷屏，真正的严重问题反而会被淹没。分级标准要写清楚，避免临场扯皮。

## 事故处理流程

事故处理流程规定质量事故从发现到闭环的标准动作，核心是"先止损、后修复、再复盘"。

1. 发现：由监控告警或人工报告触发，记录事故类型、受影响的表与时间。
2. 止损：对外口径先标注异常或暂停发布，防止错数继续外流。
3. 定位：查明直接受影响的表与下游影响范围，确认成因。
4. 修复：按成因处理，如重跑当天任务并补数、修复 SQL 后回刷、清理重复分区后重跑、补齐维表后重跑。
5. 验证：修复后重跑质量检查，确认主键唯一、非空、对账、波动全部通过。
6. 复盘：记录成因与改进项，防止同类问题复发。

事故处理最忌讳跳过止损直接修。错数一旦被业务当事实用出去，纠正成本远高于暂停发布。定位时要把下游影响范围列全，避免只修了直接表、漏了间接依赖的表。每次事故都要复盘留档，把一次性修复沉淀成长期改进。补数时要确认补的是正确口径、正确日期范围，补完再跑一遍全套质量检查，不能补完就直接放行。对账在修复后尤其重要，它是确认"真的修好了"而不是"看起来修好了"的最后一道关。

## 质量报告

质量报告定期汇总质量状况，让团队和管理层对数据健康度有统一认知。

1. 报告按固定周期出具，覆盖五个质量维度的检查通过率。
2. 报告列出当期告警数量、按一二三级分布、平均处理时长。
3. 报告列出当期事故及其成因分类，例如产出延迟、数据重复、分区缺失、关键字段为空、计算结果偏差。
4. 报告跟踪噪声表规模，提示清理进度，当前噪声表 3175 张、有效表 123 张。
5. 报告只基于有效表的监控数据，噪声表不计入质量口径。

质量报告的作用是把零散的告警和事故汇成趋势，看出问题是在收敛还是恶化。例如某类成因反复出现，就说明要从机制上改，而不是每次救火。报告也是推动噪声清理的抓手：当看到 3175 张噪声仍是 123 张有效表的二十余倍，清理的优先级自然会被重视。报告要定期发给团队和管理层，用同一套口径说话，避免各团队自说自话。对反复出问题的表要专门点名跟踪，直到其检查通过率稳定达标为止。

## 责任划分

责任划分明确每张表的质量归属，避免出了问题互相推诿，核心是"谁产出、谁负责"。

1. 每张有效表归属唯一的责任团队，负责其完整性、唯一性、准确性、一致性、时效性。
2. 上游团队对自身产出的质量负责，下游发现问题先回溯到产出方。
3. 对账差异由下游发起、上游配合定位，最终由引入偏差的那一层负责修复。
4. 噪声表的清理责任归属各自的域团队，限期并表或下线。
5. 跨团队事故由数据平台侧牵头协调，各产出方按归属分工修复。

责任清晰是质量能持续改进的前提。表无主，告警就无人认领，事故就无人复盘。责任划分要落到团队与表的对应关系上，并随建表评审同步登记。只有把"这张表归谁管"写死，质量规范才能真正落地，而不是停在纸面。登记时要一并记录值班联系方式和升级路径，确保一级告警半夜触发也能找到人。噪声清理的责任同样不能悬空：各域团队要对自己域下的 `_bak`、`_old`、`tmp_`、`u_` 以及无前缀分表负责，按保留策略限期并表或下线，把 3175 张噪声逐步压下去，而不是任其继续堆积拖累全库的检索与维护。
