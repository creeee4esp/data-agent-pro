# 数据仓库分层规范

## 分层总览

数据仓库采用五层架构，自下而上依次为 `ods_` 贴源层、`dim_` 维度层、`dwd_` 明细层、`dws_` 汇总层、`ads_` 报表层，数据加工只允许自下而上单向流动。

1. 各层职责边界清晰，禁止跨层越级生产：`ads_` 不得直接读取 `ods_`，必须经过中间各层沉淀。
2. 层内加工以本层及其直接上游为输入，加工口径一致性由上游负责保证。
3. 全库现有有效表 123 张，噪声表 3175 张。分层规范只约束 123 张有效表的生产与引用；3175 张噪声表不属于任一有效分层，不得进入生产链路。
4. 分区字段统一为 `dt`，表示分区日期，用于按天切分存储；业务日期另有 `order_date`、`pay_date` 等专用字段，承担业务口径归属。

分层的意义在于把"原始、清洗、聚合、应用"四件事拆开，让每一层只解决一类问题。贴源层解决"接得进来"，明细层解决"洗得干净"，汇总层解决"算得通用"，报表层解决"用得直接"。各层不越位，整条链路才能稳定可维护，口径才能追溯到源。

本章为总览，后续各章分别给出每一层的强制条款与推荐做法。凡本规范未明确之处，以"单向流动、职责不越位"为基本原则类推执行。

## ODS 贴源层

ODS 贴源层以 `ods_` 为前缀，保存与业务系统结构基本一致的原始数据，是全仓库唯一允许从业务系统直接接入的层。

1. 贴源层表结构应与来源系统保持一致，禁止在贴源阶段做口径加工、字段改名或指标计算。
2. 贴源层仅做必要的类型对齐和分区落地，分区字段统一为 `dt`。
3. 贴源层禁止对外提供分析口径，分析师与数据智能体不得直接查询 `ods_` 表出报表数据。
4. 贴源层数据的清洗与去重在下游 `dwd_` 层完成，贴源层只负责"原样接入、按天分区"。

贴源层的价值是保留一份忠实于业务系统的原始副本，一旦下游口径出现争议，可回溯到贴源层核对。正因如此，贴源层禁止被篡改语义，也禁止承担报表职责。任何需要对外的指标，必须经明细、汇总、报表三层加工后才能发布。

## DIM 维度层

DIM 维度层以 `dim_` 为前缀，存放可供多张事实表关联的维度信息，例如用户维度。

1. 维度层表供全仓库共享关联，应保证维度键稳定、无重复。
2. 维度的历史版本以带 `_his` 后缀的归档表保存，例如 `dim_user_his` 属于历史归档类表，不是当前生效的维表，禁止在生产链路中当作当前维度使用。
3. 维度层禁止承载事实度量，度量应落在 `dwd_` 或 `dws_` 层。
4. 维度层表变更须评估对下游所有关联方的影响，避免维度键或口径变动引发下游错配。

需要强调的是，`dim_user_his` 这类 `_his` 表是归档副本，全库 `_his` 类历史归档表共 13 张。它们记录的是维度的历史快照，仅用于追溯，不代表当前维度状态。生产作业若误引用 `_his` 表，会把过期维度带入当前口径，属于严重错误。

## DWD 明细层

DWD 明细层以 `dwd_` 为前缀，保存经过清洗、去重、关联维度后的事实明细，一行通常对应一笔业务事件。

1. 明细层是口径的第一道"定稿"层，字段清洗、空值处理、维度关联均在此完成。
2. 明细层表的旧版本以 `_old` 后缀隔离，例如 `dwd_item_review_di_old`、`dwd_trade_pay_di_old` 均为明细表旧版本，禁止在新链路中引用。全库 `_old` 类旧版本表共 44 张。
3. 明细层应保留足够粒度，供上层 `dws_` 按不同维度聚合；不得在明细层提前做不可逆的汇总。
4. 明细层的业务日期以专用字段承载，例如 `order_date`、`pay_date`，分区仍用 `dt`，两者不得混用。

明细层是上层一切汇总的共同起点，口径一旦在此定错，向上会被逐层放大。因此当明细表升级时，旧版本必须改名加 `_old` 并停止写入，由新版本接管生产，`dwd_trade_pay_di_old` 这类命名正是这一约定的产物，提醒使用者它已退役。

## DWS 汇总层

DWS 汇总层以 `dws_` 为前缀，按业务域、粒度、事件、周期对明细做轻度聚合，命名遵循 `dws_<域>_<粒度>_<事件>_<周期>`，周期为 1d / 1w / 1m，例如 `dws_trade_prov_order_1d`。

1. 汇总层的日、周、月三张表构成一个家族，同一家族仅周期后缀不同，例如家族前缀 `dws_trade_brand_order`、`dws_trade_cate1_order` 各自派生 1d / 1w / 1m 三张表。
2. 汇总层应以 `dwd_` 明细为输入，禁止跨过明细层直接聚合 `ods_` 数据。
3. 汇总层度量须标注可加和性：可加和的度量允许跨行求和，不可加和的比率、平均值必须用分子分母重算，禁止直接相加。
4. 汇总层按域组织家族，例如商品评价域有 `dws_item_brand_review`、`dws_item_cate1_review`、`dws_item_sku_review`，物流发货域有 `dws_lgs_carrier_ship`、`dws_lgs_prov_ship`、`dws_lgs_warehouse_ship`，各家族职责不重叠。

汇总层的作用是把高频、通用的聚合固化下来，避免每个需求都从明细现算。选择日、周、月哪一张，取决于分析所需的时间粒度：跨任意天数的灵活统计用 1d，固定自然周用 1w，固定自然月用 1m。家族化命名使同一业务含义的三种周期一目了然，便于使用者按需取用。

## ADS 报表层

ADS 报表层以 `ads_` 为前缀，直接面向报表与业务口径，是对外发布数据的唯一出口层。

1. 报表层表按报告期命名，例如 `ads_trade_gmv_daily` 为按日报表，`ads_coupon_usage_monthly`、`ads_item_review_score_monthly`、`ads_lgs_delivery_monthly`、`ads_pay_channel_monthly`、`ads_trade_cate1_sales_monthly` 为按月报表。
2. 报表层以 `dws_` 汇总或 `dwd_` 明细为输入，禁止直接读取 `ods_` 贴源数据。
3. 报表层月报的报告期以专用统计字段承载，例如月报表用 `stat_month` 标识报告月，禁止在月报表上以 `dt` 充当业务报告期。
4. 报表层的指标口径一经发布即对外生效，变更须走变更评审并通知下游使用方。

报表层是业务同事和数据智能体最常直接查询的层，因此对口径稳定性要求最高。需要特别注意报告期字段：`ads_pay_channel_monthly` 这类月报的报告月在 `stat_month` 上，不在 `dt` 上，取数时不得张冠李戴。报表层只发布经过前序各层沉淀的结果，不承担清洗与明细加工职责。

## 跨层引用规则

跨层引用必须自下而上、就近取用，即每一层只允许引用其直接下游层或同层已定稿的产物。

1. 引用方向强制单向：`ads_` ← `dws_` ← `dwd_` ← `dim_`/`ods_`，禁止反向引用，禁止下游污染上游。
2. 禁止越级引用，例如 `ads_trade_gmv_daily` 不得直接 FROM `ods_` 表，必须经由 `dws_` 或 `dwd_` 取数。
3. 事实表关联维度时，只能关联当前生效的 `dim_` 维表，禁止关联 `dim_user_his` 这类历史归档维表。
4. 任何层都禁止引用噪声表作为生产输入，包括 `_bak`、`_bak_日期`、`_old`、`_his`、`test_`、`tmp_`、`u_` 以及无前缀的月分表、日分表。

越级与反向引用会破坏分层的可追溯性，使口径无法定位到唯一来源。就近引用则保证每一层的输入边界清晰，出现偏差时可逐层回退排查。引用维表时尤其要确认引用的是当前维表而非 `_his` 归档，否则会把过期维度混入当前口径。

## 分层选表原则

分层选表原则用于指导使用者在同一业务含义的多张表之间，选出正确的那一张，核心是"用正表、按粒度、看报告期"。

1. 对外统计一律使用有效表，全库有效表共 123 张；禁止使用 3175 张噪声表中的任何一张出口径。
2. 需要固定报告期的结论，优先用 `ads_` 报表层，例如月度 GMV 用 `ads_trade_gmv_daily` 按月汇总或相应月报表。
3. 需要灵活时间范围或多维下钻，用 `dws_` 汇总层，并按所需粒度选择 1d / 1w / 1m，例如省份维度日粒度用 `dws_trade_prov_order_1d`。
4. 需要最细明细或自定义口径，回到 `dwd_` 明细层重算，不要在报表层硬凑。

选表时先问三件事：要的是固定报告期还是灵活区间、要的是哪一个粒度、口径是否已有现成报表。按这三点对照分层职责，基本能唯一确定该用哪张表。遇到看似同义的多张表，务必排除带噪声特征的那些，只在有效表范围内选择。

## 数据保留策略

数据保留策略规定各类表的留存方式，核心是"正表长期维护、归档只做追溯、噪声限期清理"。

1. 有效表长期保留并持续维护，按 `dt` 分区留存历史数据，保留周期由各域按业务需要约定。
2. 历史归档表以 `_his` 后缀保存，仅用于追溯，不参与生产，全库 `_his` 类共 13 张。
3. 备份与带日期备份以 `_bak`、`_bak_日期` 标识，属临时留存，用后应限期清理；全库 `_bak` 类 98 张、带日期备份类 510 张。
4. 旧版本以 `_old` 标识退役后应限期下线，全库 `_old` 类 44 张；临时表 `tmp_` 类 66 张、个人副本 `u_` 类 345 张、测试表 `test_` 类 58 张均不得长期堆积。
5. 无前缀的月分表、日分表属历史遗留残片，月分表 216 张、日分表 1825 张，应逐步并入正表后清理。

保留策略的目标是控制噪声增长。当前 3175 张噪声已是 123 张有效表的二十余倍，若备份、副本、分表无限期堆积，检索与维护成本将持续恶化。因此除长期维护的正表外，其余各类均须设定清理节奏并定期执行。

## 常见反模式

常见反模式是本规范反复出现问题的集中清单，列出以供评审时逐条对照，任一命中即判定不合规。

1. 越级生产：`ads_` 直接读 `ods_`，跳过 `dwd_`、`dws_`，使口径无法追溯。
2. 误用归档维表：生产作业关联 `dim_user_his` 而非当前维表，把历史维度带入当前口径。
3. 误用旧版本明细：链路里仍引用 `dwd_item_review_di_old`、`dwd_trade_pay_di_old`，而未切换到新版本。
4. 误把备份当正表：拿 `ads_item_review_score_monthly_bak`、`ads_lgs_delivery_monthly_bak`、`ads_pay_channel_monthly_bak` 出口径，或使用带日期备份 `ads_trade_cate1_sales_monthly_bak_20250309`。
5. 误用测试表：对外统计引用 `test_ads_item_review_score_monthly`、`test_ads_pay_channel_monthly`、`test_ads_trade_cate1_sales_monthly`。
6. 误用临时表与个人副本：生产引用 `tmp_aftersale_order_0221`、`tmp_category_di_1226` 或 `u_chenqi_channel_monthly_tmp`、`u_chenqi_coupon_di_analysis`。
7. 误用分表：以为 `item_review_202301` 或 `log_visit_20250101` 是完整表，实际只含某月或某天的残片数据。
8. 分区当业务日期：所有过滤写在 `dt` 上，用 `dt` 代替 `order_date`、`pay_date` 做业务归属，导致补数回刷污染口径。
9. 报告期字段错配：在月报表上找 `dt`，而非使用 `stat_month` 标识报告月。

这些反模式之所以反复发生，根源是使用者凭表名字面或印象取数，而未核对分层职责与噪声特征。逐条对照本清单，可在评审阶段把绝大多数口径事故挡在上线之前。
